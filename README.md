# Лабораторная работа №2: Отношения между классами и операции над объектами

> **Дисциплина:** Объектно-Ориентированное Программирование  
> **Вариант:** 22

---

### 📌 Цель работы
Изучить принципы и механизмы установления связей между объектами в ООП (агрегация, композиция, ассоциация), а также реализовать наследование, полиморфизм и перегрузку операторов.

---

### 📂 Задания и реализация

#### Задание 1: Агрегация классов (Автомобиль и Колесо)
- **Условие:** Реализовать агрегирование классов. Создать объект класса `Автомобиль`, используя класс `Колесо` как атрибут.
- **Код:** [Task1_Aggregation](./Task1_Aggregation)
- **Ключевые особенности:**
  - Класс `Wheel` (Колесо) существует независимо от класса `Vehicle` (Автомобиль)
  - Автомобиль содержит указатель на объект Колеса: `Wheel* obj_wheel`
  - Демонстрация того, что после уничтожения автомобиля колесо продолжает существовать
  - Реализованы конструкторы, деструкторы и методы для обоих классов

#### Задание 2: Система "Железнодорожная касса" (UML + Полиморфизм)
- **Условие:** Спроектировать систему, где Пассажир делает Заявку на поездку, система ищет подходящий Поезд, Администратор оформляет Счет. Построить UML-диаграмму классов.
- **Код:** [Task2_RailwaySystem](./Task2_RailwaySystem)
- **UML-диаграмма:**

- **Ключевые особенности:**
  - **Наследование и интерфейсы:** Класс `Bill` реализует интерфейс `IPrintable` с чистым виртуальным методом `printDocument()`
  - **Композиция:** Класс `Date` содержит объект `Time` (время не существует без даты)
  - **Ассоциация:** `RailwayTicketOffice` управляет массивом поездов (`Train* m_trains[MAX_TRAINS]`)
  - **Агрегация:** `Bill` содержит указатели на `Request` и `Train` (существуют независимо)
  - **Инкапсуляция:** Все атрибуты приватные, доступ через геттеры
  - **Полиморфизм:** Использование указателя на базовый интерфейс `IPrintable* doc = myBill`
  - **Управление памятью:** Корректное удаление динамически созданных объектов в деструкторе `~RailwayTicketOffice()`

#### Задание 3: Перегрузка оператора == (Комплексные числа)
- **Условие:** Создать класс `ComplexNumber` и перегрузить оператор `==` для сравнения двух комплексных чисел.
- **Код:** [Task3_ComplexNumber](./Task3_ComplexNumber)
- **Ключевые особенности:**
  - Перегрузка оператора сравнения: `bool operator==(const ComplexNumber& other) const`
  - Сравнение происходит по обоим компонентам: действительной (`m_real`) и мнимой (`m_imaginary`) частям
  - Реализован конструктор и метод вывода `print()`

### 🎯 Что было изучено и реализовано:

**Типы отношений между классами:**
- ✅ **Агрегация** — слабая связь ("has-a"), объект-часть может существовать отдельно (Автомобиль и Колесо)
- ✅ **Композиция** — сильная связь, объект-часть не существует без целого (Date и Time)
- ✅ **Ассоциация** — общая связь между объектами (Passenger и Request)
- ✅ **Наследование** — класс `Bill` наследует от интерфейса `IPrintable`

**Принципы ООП:**
- ✅ **Инкапсуляция** — все данные приватные, доступ через публичные методы
- ✅ **Полиморфизм** — использование интерфейса `IPrintable` для разных типов документов
- ✅ **Перегрузка операторов** — оператор `==` для сравнения комплексных чисел
- ✅ **Перегрузка методов** — несколько конструкторов с разными параметрами

**Работа с памятью:**
- ✅ Динамическое создание массивов объектов (`new Train[MAX_TRAINS]`)
- ✅ Корректное освобождение памяти в деструкторах (`delete[] array`)
- ✅ Использование указателей для реализации агрегации

### 💡 Выводы и инсайты

В ходе выполнения лабораторной работы:
1. **Понял разницу между агрегацией и композицией:** 
   - Агрегация — это когда объект может существовать отдельно (Колесо может существовать без Автомобиля)
   - Композиция — когда часть не может существовать без целого (Time является частью Date)

2. **Научился проектировать систему с помощью UML:** 
   - Сначала нарисовал диаграмму классов с отношениями
   - Затем реализовал код строго по диаграмме
   - Это помогло избежать ошибок в архитектуре

3. **Освоил работу с интерфейсами:** 
   - Интерфейс `IPrintable` позволяет печатать разные типы документов
   - Это пример полиморфизма: один интерфейс — множество реализаций

4. **Закрепил управление памятью:** 
   - Научился корректно удалять массивы объектов в деструкторе
   - Понял важность `delete[]` для предотвращения утечек памяти
